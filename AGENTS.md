# AGENTS.md

## Purpose

This repository is a .NET solution with some Rust-backed native assets and code generation. Use this file as the default guidance for autonomous coding agents working in this repo.

## Working conventions

- Prefer small, targeted changes over broad rewrites.
- Keep edits scoped to the relevant project or feature area.
- Follow the existing repository structure and naming conventions.
- Preserve public API compatibility unless the task explicitly requires a breaking change.
- Favor readable, idiomatic C# code and minimal additional dependencies.
- The repository's .editorconfig files are authoritative for all .NET/C# coding conventions, formatting, and style rules; follow them exactly in any C# or .NET changes.
- In native projects, prefer writing Rust-based code over C/C++ when equivalent functionality can be implemented in Rust.
- When code is generated by AI, mark it clearly with a start and end comment so it is obvious to reviewers and maintainers.
- For AI-generated code, the start marker should include, if feasible, the model name and version used, e.g. `// AI GENERATED START - model: Claude Sonnet 4.6` or `// AI GENERATED START - model: GPT Terra 5.6`.
- AI-generated commits must include a co-authored trailer in the commit body, e.g. `Co-authored-by: ...`.
- Use conventional commits for commit messages, and do not omit the body.
- Respect the repository commit template in `.gitmessage` when crafting commit messages: use the conventional-commit subject format and include the required body and `Co-authored-by:` trailer as applicable.
- If code is copied from the internet, such as blog posts, Stack Overflow answers, or sample code, include the source link and verify the license and copyright are compatible with this project’s license before using it.
- Do not copy code from external sources without confirming compatibility with the repository license and providing the required attribution.

## Build and validation

- Use the repository's standard .NET build/test flow for validation.
- Prefer the smallest relevant command that checks the changed behavior.
- If a project-specific test suite exists, run the narrowest relevant test target rather than the entire solution unless the task requires broader validation.
- Do not claim success without fresh verification output.

## Repository layout

- `src/` contains library source projects.
- `tests/` contains test projects.
- `build/` contains repo build configuration and shared .targets/.props files.
- `artifacts/`, `obj/`, and `target/` are generated outputs and should not be edited manually.
- `gen/` contains generated sources or generators.

## Coding guidance

- Match surrounding style and patterns already used in the file or project.
- For .NET/C# files, the .editorconfig settings are the source of truth for formatting and naming rules; do not override them with ad hoc conventions.
- Keep methods and classes focused and easy to reason about.
- Maintain a moderate comment-to-code ratio: comments should explain intent and the reasoning behind a decision, not restate the implementation.
- Prefer comments that state the why, not the what; write intent-focused notes only when the code alone would not make the decision clear.
- Update tests when behavior changes or a bug is fixed.
- Do not add test-only hooks to production code.
- Avoid speculative refactors unrelated to the requested work.
- When generating or editing code with AI assistance, add explicit start and end markers around the generated section, e.g. `// AI GENERATED START - model: <name/version if known>` and `// AI GENERATED END`.
- For all copied code, document provenance: source URL, author if available, license, and compatibility assessment with the repository license.
- If a copied snippet’s license is unclear, incompatible, or cannot be verified, do not include it.
- Keep code within practical maintainability thresholds: prefer no more than 120 characters per line, avoid methods longer than about 20-30 lines, keep cyclomatic complexity low, and avoid classes that grow beyond a single responsibility or roughly 200-300 lines without justification.

## Architectural rules

- Within the same folder, projects may not reference each other.
- `gen` must not reference `gen`.
- `src` must not reference `src`.
- Exception: C# projects in `src` may reference native Rust-backed projects when required for interop or integration.
- `tests` must not reference `tests`.
- `shared` must not reference `shared`.
- `src` may reference `gen`.
- `src` may reference `shared`.
- `tests` may reference `shared`.
- `tests` may reference `src`.
- `tests` may reference `gen`.
- Keep dependency direction explicit and acyclic: prefer lower-level abstractions in `shared` or `gen` and consume them from `src` or `tests`, rather than creating circular or sibling references.
- Do not introduce new project-to-project dependencies that violate the above layering rules.

## Complexity and size conventions

- Prefer a maximum line length of 120 characters unless a repository-specific .editorconfig rule imposes a stricter limit.
- Prefer methods to remain small enough to read in one screen; avoid large monolithic methods and split responsibilities when logic exceeds a single well-defined concern.
- Keep McCabe cyclomatic complexity low; if a method grows beyond a simple decision tree, consider extracting helper methods or reducing branching.
- Keep classes focused; if a class grows beyond a single responsibility or becomes difficult to navigate, refactor it into smaller types rather than adding unrelated members.
- Favor readability and separation of concerns over clever one-liners or deeply nested logic.

## Testing guidance

- Check whether a related test project exists before adding a new one.
- Prefer real behavior verification over mock-heavy tests.
- For Rust-based code, prefer unit tests in the same module or crate, plus integration tests when behavior crosses crate boundaries.
- For native Rust-backed components, validate edge cases, panic behavior, error handling, and FFI boundaries with targeted tests rather than relying only on C# smoke tests.
- Maintain a high level of coverage for changed behavior; 100% is not required, but coverage should not fall below roughly 80-90% for the affected code paths.
- If coverage drops below that range for a changed area, add meaningful tests before concluding the change is complete.

## When working in this repo

- Prefer real behavior verification over mock-heavy tests.
- If you need to investigate a failing build or test, identify the root cause before changing code.
- If a task is ambiguous, make the smallest safe assumption and keep the change narrowly scoped.
